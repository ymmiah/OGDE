Open framework · engineering preview

Verified intelligence, matched where the assets already are.

OGDE is a privacy-first framework for cyber defence. It is meant to help an organisation identify, prioritise and — only with a person’s approval — respond to threats it can evidence, without handing over its systems, its data, or the decision to act. It is not another CVE list and not a chatbot.

Get started Documentation View source

v0.2.2 is the published command-line baseline. v0.3, the verified loop, is in development. This is not a deployed protection network, and the five-site pilot gate has not been met.

Four rules the software is built around

  1. Local control

    Inventories are collected on the operator’s machine. OGDE does not upload them by default.

  2. Separate trust from truth

    A valid signature shows who published a record. It is not evidence that the affected range is correct.

  3. Fail closed

    Missing trust, a bad schema, an expired feed or a mismatched digest is rejected. It is not quietly accepted.

  4. A person decides

    Findings recommend review. They do not patch, isolate or change a production system.

The verified loop

One pass, from a local inventory to a human decision.

v0.3 has to prove this loop for WordPress sites and CI lockfiles before later operational phases start. The pilot — five authorised sites for four weeks, with a published false-positive rate — has not been run.

  1. 01

    Discover locally

    ogde inventory reads WordPress version headers and Composer or npm lockfiles on the operator’s machine. A broader consent-based agent is planned. The collector does not open wp-config.php, secrets or databases.

  2. 02

    Validate the advisory

    ogde assess checks an Ed25519 signature against a publisher key pinned out of band, then rejects tampered, expired, replayed or rolled-back feeds. Provenance, freshness and TUF or Sigstore distribution are still being hardened or only specified.

  3. 03

    Match the inventory

    The preview compares exact versions. It does not yet apply every ecosystem’s range rules, and it does not upload the inventory to do the match.

  4. 04

    Prioritise, and say why

    ogde report orders local findings by a KEV flag, then EPSS, then severity, then exposure, and prints the factors. Business criticality and mitigations beyond a VEX statement are not a finished model.

  5. 05

    Keep the uncertainty visible

    A signature does not make a claim true. When sources disagree, both claims stay. A suppressed finding remains in the local audit file.

  6. 06

    Decide, then share only on purpose

    Nothing in the preview remediates a system. Narrow response integrations, and any federated sharing, are future work and would stay voluntary.

A WordPress plugin shows up in an advisory

The useful outcome is specific: the advisory was signed by a publisher you pinned, the installed version is or is not inside the claimed range, and the report says how confident that match is. OGDE should not mark every site compromised, and it should not edit the site.

Capabilities

What the repository actually does.

Names below match the command-line preview on main. Planned surfaces are listed so the shape of the framework is visible. They are not shipped products.

Capability Stage What that means
Signed advisory assessment Implemented Ed25519 verification, a pinned publisher, exact-version matching and a local assessment. ogde trust-add, ogde assess, ogde scan.
Local inventory Implemented CycloneDX from a WordPress tree, composer.lock and package-lock.json. Python environments can be listed with ogde inventory-python. Nothing is uploaded.
Finding report Implemented Confidence, disagreement between sources, VEX suppression and a local audit file. Optional OSV queries exist only behind --confirm-inventory-sharing.
Offline KEV handling Experimental A local snapshot can be checked against a pinned digest. OGDE does not fetch CISA, and a catalogue match is not proof that this asset is being exploited.
TUF and Sigstore Specification Roles, expiry and identity pinning are documented. The libraries are not dependencies, and the client still uses the Ed25519 verifier.
Response and sharing Planned No autonomous remediation. Future integrations would be narrow and authorised. Federated sharing would be voluntary and minimised. Neither exists as a service.

Product areas

Four areas. One of them is in your hands today.

The names describe the intended platform. Only the developer tools exist as software you can run. There is no released console to screenshot.

Developer tools

The Python package and ogde command: signed feeds, local inventory and finding reports. Later CI gates and SARIF are not in this preview. odge remains a compatibility alias.

Planned

Consent-based local collection, read-only, for more than a lockfile. Not a released Linux agent. Collection rules would be an allow-list, not a search of the disk.

Planned

Intelligence network

Trusted, federated sharing between organisations that choose to contribute. Not operational. A publisher can describe a vulnerability. It cannot instruct another organisation’s systems.

Roadmap

Workstreams, not twelve shipped versions.

These workstreams describe the product. They do not replace the repository’s engineering sequence, M3 to M8. The v0.3 pilot gate still has to be met before later operational phases.

  1. 01

    Security foundation

    Python core, signatures, privacy limits, anti-rollback and continuous tests.

    In progress
  2. 02

    Verified intelligence

    KEV, OSV, EPSS, provenance and publisher authentication. Live fetches are not the default.

    In progress
  3. 03

    Inventory and matching

    WordPress and lockfiles are in the preview. Broader version-range matching is not.

    Early
  4. 04

    Risk prioritisation

    Exploit signals, exposure, confidence and VEX, with the reason printed beside the rank.

    Partial
  5. 05

    Local agent

    Read-only collection on Linux, with the owner’s consent and a field allow-list.

    Planned
  6. 06

    Audit storage

    Append-only local evidence, replay protection and checkpoints a reviewer can re-check.

    Prototypes
  7. 07

    Dashboard and API

    A console, authenticated APIs and review queues. Not in this preview.

    Planned
  8. 08

    Assisted explanation

    Optional text that cites the evidence. It would not be allowed to override policy.

    Planned
  9. 09

    CI integrations

    A build gate, SARIF and SBOM output beyond the current exit code.

    Planned
  10. 10

    Federated defence

    More than one publisher, with revocation and a namespace each publisher cannot leave.

    Planned
  11. 11

    Organisation operations

    Sign-in, tenancy, monitoring and backups for a future hosted tier. This website has none of those.

    Planned
  12. 12

    Validation

    Independent review, a measured pilot and an honest production claim.

    Planned

Near-term engineering

None of this is checked off by this website. The sequence is to audit the open M3 changes, dependencies and CI; consolidate what is reviewable; run the full tests; keep adversarial cases for bad signatures, replay, rollback, corruption and filesystem tricks; write down trust and checkpoint assumptions; rehearse a synthetic end-to-end demo; define the pilot protocol; then ask for a human security review.

First success, not yet claimed

Five authorised pilot sites over four weeks. A defined false-positive rate, published. Findings that can be reproduced from evidence. Regression, integration and security tests. No unauthorised transfer or remediation. A person approves every consequential change.

Get started

Run the preview on your own machine.

The commands below use the synthetic fixture in the repository. They do not contact OSV, KEV, EPSS or Wordfence, and they do not change a WordPress site. ogde report exits 2 when the example still has a visible finding. That is the demonstration, not an error.

  • v0.3 specification
  • Signed-feed walkthrough
  • Security policy
  • Repository

Local quickstart

git clone https://github.com/ymmiah/OGDE.git
cd OGDE
python -m pip install -e .
mkdir -p .ogde-local

ogde inventory \
  --wordpress examples/demo-site/wordpress \
  --composer-lock examples/demo-site/composer.lock \
  --package-lock examples/demo-site/package-lock.json \
  --out .ogde-local/inventory.cdx.json

ogde report \
  --findings examples/findings.example.json \
  --vex examples/vex.example.json \
  --out .ogde-local/findings.json \
  --markdown .ogde-local/findings.md

Contribute without sending us your inventory.

Read the security policy before you report a vulnerability. Do not test OGDE against systems you do not have permission to assess. Pull requests are reviewed in the open repository. The software licence is MIT. Data-source terms, when a feed is published, will be recorded separately.
